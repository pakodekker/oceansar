# SAR raw generation, system errors and focusing

`oceansar.radarsim.sar_raw_nompi.sar_raw` writes ideal, uncalibrated complex
samples to `[sim] raw_file`. Its scalar `cal_factor` converts simulator field
amplitudes to the calibrated raw-data amplitudes previously produced by the
raw generator. Geometry, channel baselines, reference range history and NRCS
metadata remain in the same file.

`oceansar.radarsim.sar_system_errors.sar_system_errors` reads that ideal file
and writes `[sim] sys_raw_file` (default `raw_data_sys.nc`). For now it applies

```
raw_system = cal_factor * raw_ideal + noise
E[abs(noise)**2] = 10**(nesz_db / 10)
```

The noise is circular complex Gaussian, with NESZ taken from `[srg] nesz`.
Set NESZ to `-inf` for calibration without receiver noise. Calibration lives
beside this noise model so a future receiver model can refer its noise back
to simulator units and defer calibration until SAR processing. No sample
quantization has been added.

The stage preserves variable dtypes and metadata and processes one channel
and polarization in blocks of pulses. Fixed `[sim] seed` gives independent,
reproducible HH/VV noise streams; changing the block size does not change the
realization. New ideal files are marked `raw_data_state=ideal`; processed files
record their calibration/noise state and cannot be passed through this stage
again. Raw files from the old generator already include calibration and noise
and must be regenerated.

Both `oceansar_sarsim` and `Notebooks/sarsim.ipynb` explicitly orchestrate these
steps whenever SAR focusing is enabled, even when ideal raw generation is skipped:

1. Call `sar_system_errors` to generate the system raw file.
2. Call `sar_focus` with that file as input.
3. Delete the temporary system raw file after successful focusing.

The orchestration stays in each entry point so reconstruction stages, including
MAPS, can be inserted there. The ideal file remains available for further noise
realizations or receiver models. An intermediate is retained when processing
fails. Downstream DC/ATI processing uses the SLC.

Standalone processing, retaining the system raw file for inspection:

```sh
python -m oceansar.radarsim.sar_system_errors -c par/sim_example_rosel.cfg
```

`sar_raw` no longer takes the unused `errors_file` and `reuse_errors_file`
arguments. Its interface is `sar_raw(cfg_file, output_file, ocean_file,
reuse_ocean_file=False, plot_save=True, bistatic=False, dau=0)`.

# Ocean initial conditions

New `ocean.nc` files use xarray with the `h5netcdf` backend. They contain native
complex `wave_coefs`, one-dimensional `kx`/`ky` axes and scalar initialization
metadata, including depth, RMS slopes and monochromatic swell phase. These are
Fourier initial conditions, not surface snapshots or a time series. Native
coefficient precision is retained, including complex128 inputs when present.

The old format used two float64 coefficient rasters and two float32 wavenumber
rasters: approximately 24 bytes per cell. A native complex64 file uses about
8 bytes per cell plus the small axes and metadata. Large existing examples
therefore shrink from roughly 615 MiB to 205 MiB without quantizing the
complex64 coefficients generated by OceanSurface. Old split-component files
are intentionally unsupported and should be regenerated.

Read new files explicitly with `xr.open_dataset(path, engine='h5netcdf')`, or
use `OceanSurface.load`. The full complex spectrum is retained; it is not
assumed Hermitian. The surface class reconstructs its in-memory grids and
propagated fields from these initial conditions.

# Shared utilities

Common numerical utilities now use `drama.utils`: FFT sizing, smoothing,
resampling, dB conversion, logging and parameter-file selection. OceanSAR keeps
its simulation-specific random streams and geometry. `oceansar.utils.misc`
contains re-exports and thin adapters for historical argument names, rather
than duplicate numerical implementations.
